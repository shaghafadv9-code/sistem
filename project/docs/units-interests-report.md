## 1) الملخص التنفيذي

نُفِّذت متطلبات المرحلة الثانية (27 بندًا) على النظام القائم **دون إعادة بناء ودون حذف أي وظيفة عاملة**، وبعد تدقيق كامل لقاعدة البيانات والخادم والواجهة أولًا. النتيجة:

- **سلسلة العقارات كاملة**: مشروع ← مبنى ← دور (بنوعه) ← وحدة ← غرف، مع فلترة مجتمعة على شاشة الوحدات.
- **سلسلة العملاء كاملة**: عميل ← اهتمامات متعددة ← مواصفات ← مطابقة ← تحديد ← واتساب ← تسجيل المتابعة.
- **نظام أنواع الأدوار**: قبو / أرضي / ميزانين / دور عادي / روف / سطح / أخرى — «روف» هو **نوع الدور**، ولا يُفترض أن الدور الخامس روفًا تلقائيًا.
- **فلترة عدد الغرف** بأشكالها: الكل / 1 / 2 / 3 / 4 / 5 / 6+ و المتقدمة = ‏> ‏< بين (مثال 3–5)، في شاشة الوحدات وشاشة الاهتمامات.
- **«غير محدد» ليست صفرًا**: أي حقل اهتمام غير محدد = لا قيد على المطابقة (لا يُستبعد العميل).
- **تصدير Excel** للنتائج **المفلترة حاليًا** فقط، بترتيب عربي RTL ومُقيَّد بصلاحية.
- **واتساب**: تجهيز الرسالة بالقالب مع استبدال اسم العميل الحقيقي وفتح المحادثة يدويًا — **لا إرسال جماعي آلي** — ويُسجَّل في سجل العميل بوصف «تم فتح WhatsApp للمراسلة» لا «تم الإرسال».
- **الاختبارات**: 46/0 (المراجعة الأساسية) + 134/0 (المالية وCRM) + **81/0 (اختبارات هذه المرحلة الجديدة)**.

### 4-2 الخادم والواجهات البرمجية

- **`estate_core.unitFilterWhere`**: عدد الغرف (`rooms=`, `rooms_op=eq|gte|gt|lte|lt|between`, `rooms_max`)، الحمامات (`bathrooms`, `bathrooms_op`)، المواقف، المساحة (`area_min/max`)، السعر (`price_min/max` ومرادفاتها)، الرابط الهيكلي (`project_id/building_id/floor_id`)، نوع الدور، و«روف» = نوع الدور روف/سطح **أو** علم `has_roof` على الوحدة.
- **`estate_core.interestFilterWhere`**: فلترة الاهتمامات بعدد الغرف بأشكاله + خيار تضمين «غير محدد» + الأعمدة الجديدة `floor_id`, `floor_pref`, `parking`, `open_units_min`, `not_contacted_days`، وبحث `q` يشمل الاسم/الجوال/الجوال البديل/البريد/الكود/الملاحظات + فلتر **موظف المبيعات** (عبر `clients.assigned_to`) و**مصدر العميل**.
- **`estate_core.matchInterestsToUnit`**: مطابقة غير صارمة بنقاط توافق (نسبة + أسباب)، حيث الحقل غير المحدد = لا قيد: غرف ±1، حمامات ±1، المساحة بتداخل النطاق، الدور، الروف، الميزانية، المشروع المفضل.
- **واجهات جديدة/معدَّلة** (14 مسارًا في `api_crm.js` + تعديلات `api.js`):

| المسار | الوظيفة |
|---|---|
| `GET /buildings?project_id=` | مبانٍ المشروع فقط، ومعها أنواع الأدوار |
| `GET /floors?building_id=` | أدوار المبنى فقط، مع `display_name` و`type_t` وعدد الوحدات |
| `GET /floors/meta` | أنواع الأدوار المتاحة للواجهة |
| `POST /buildings/:id/floors` / `PUT /floors/:id` / `DELETE /floors/:id` | إدارة الأدوار بنوعها |
| `GET /interests` | فلترة كاملة + `ids` (معرّفات النتائج الحالية لتحديد الكل) |
| `GET /interests/meta` | قوائم الفلاتر (مشاريع/أدوار/موظفون/مصادر/مراحل…) |
| `GET /interests/excel` | تصدير النتائج المفلترة (22 عمودًا عربي RTL) |
| `POST /interests/messages` | تجهيز الرسائل بالقالب واستبدال المتغيرات (بلا إرسال) |
| `POST /interests/log-contact` | تسجيل «تم فتح WhatsApp للمراسلة» في سجل العميل |

| `POST/PUT /units` | ربط الوحدة بالدور والتحقق من أن الدور يتبع المبنى والمشروع |
| `GET /units` | الفلاتر المجتمعة (بعد إصلاح موضّح في القسم 6) |
| `GET /projects/:id/tree` | شجرة المشروع (مشروع ← مبانٍ ← أدوار ← وحدات) |

### 4-3 الواجهة الأمامية

- **شاشة الوحدات والمشاريع** (`client/src/pages/Projects.jsx`): لوحة فلاتر (المشروع/المبنى/الدور/نوع الدور/روف/عدد الغرف سريع ومتقدم/نوع الوحدة/الحالة/السعر/المساحة/بحث)، عرض بطاقات المشاريع ثم الوحدات، شجرة المشروع (مشروع ← بناء ← أدوار بشارة النوع و«روف»)، نماذج إضافة/تعديل الوحدة باختيار متسلسل **مشروع ← مبنى ← دور** (المباني تُفلتر بالمشروع والأدوار بالمبنى)، نموذج إدارة الأدوار (إضافة/تعديل/حذف مع النوع)، زر **«المهتمون»** لكل وحدة يعرض العملاء المهتمين بنسبة التوافق وأسبابها + «فتح ملف العميل» + «واتساب» + تصدير Excel.
- **شاشة اهتمامات العملاء** (`client/src/pages/Interests.jsx`): قسم مستقل في القائمة الجانبية، مؤشرات أعلى الصفحة، شريط بحث + فلاتر متقدمة، الترتيب المطلوب: بحث/فلاتر ← عدد النتائج ← [تحديد الكل][تصدير Excel][مراسلة WhatsApp] ← الجدول (المشكلة بلا مرادفات مُربكة)، ونموذج اهتمام يختار عميلًا قائمًا ويعرض بياناته تلقائيًا (الاسم/الجوال/الجوال البديل/البريد/المدينة/الموظف/المصدر) **قراءة فقط من جدول العملاء** بلا أي تكرار، مع نافذة الرسائل (نسخ + فتح واتساب + الجوال البديل) وتسجيل المتابعة قبل الفتح.
- **شاشة العملاء**: عند القدوم من زر «فتح ملف العميل» يُفتح ملف العميل المطلوب تلقائيًا (عبر مفتاح جلسة `ss_open_client`) — إضافة صغيرة بلا أي تغيير في وظائف الشاشة.

## 5) دلالات مهمة مثبَّتة في النظام

1. **«روف» نوع دور**: يُخزَّن في `floors.type` ويظهر في العرض «الدور الخامس — روف». يمكن أن يكون الدور الخامس روفًا في مشروع وعاديًا في آخر — **لا افتراض تلقائي ولا رقم ثابت**.
2. **عدد الغرف رقم فعلي** لا نص، وفلاتر الغرف تجتمع مع كل الفلاتر الأخرى (مشروع/مبنى/دور/سعر/مساحة/حالة).
3. **غير محدد ≠ صفر**: الحقل الفارغ في الاهتمام = لا قيد. تُعرض «غير محدد» ولا تُستبعد بسببه، ويوجد خيار صريح لتضمين غير المحدد عند الحاجة.
4. **المطابقة غير صارمة**: غرف فقط بدون ميزانية أو مشروع → يُطابق أي وحدة مناسبة، بترتيب أفضلية بنسبة توافق وأسباب.
5. **Excel = النتائج الحالية**: التصدير يستقبل نفس فلاتر الشاشة ويعيد ما تراه العين لحظيًا فقط.
6. **الوحدة مرتبطة بالدور بمرجع** (`units.floor_id`)، ويُرفض أي دور لا يتبع المبنى/المشروع المختار (خطأ 400 برسالة عربية واضحة)، ولا يُخزَّن اسم الدور كنص.
7. **واتساب فتح لا إرسال**: النظام يُجهّز النص ويستبدل `{{اسم العميل}} {{اسم المشروع}} {{نوع العقار}} {{عدد الغرف}} {{السعر}}` ثم يفتح المحادثة ليرسل الموظف بنفسه، ويُسجَّل «تم فتح WhatsApp للمراسلة» مع التاريخ والوقت والموظف والاهتمام/الوحدة. البنية جاهزة للربط بـ WhatsApp Business API لاحقًا (`message_templates` موجود).
8. **الصدق في السجل**: لا يُسجَّل أي شيء على أنه «تم الإرسال» ما لم يُثبَت، والتصدير الحساس مُقيَّد بصلاحية `interests:export`.

## 6) أخطاء اكتُشفت أثناء التحقق وأُصلحت (قبل التسليم)

| الخطأ | الأثر | الإصلاح |
|---|---|---|
| `resource()` في `api.js` يتوقع `{sql}` بينما `unitFilterWhere` يعيد `{where}` | **فلاتر الغرف المتقدمة/المساحة/السعر داخل شاشة الوحدات كانت تُتجاهَل صامتًا** | توحيد الواجهة لدعم `{sql}` و`{where}` + تمرير كل مفاتيح الفلترة للفلتر الموحّد واستثناؤها من المعالجة العامة |
| `normalizeInterest` كان يصفّر الأرقام الغائبة | تحديث جزئي للاهتمام يمسح الغرف/الحمامات/المساحة | التحويل فقط عند إرسال الحقل فعليًا (تحقق عبر `PUT` جزئي: بقي `floor_id=61` و`rooms=5`) |
| التحقق من الدور كان قبل التطبيع | قبول دور من مشروع آخر خطأً (201 مع `floor_id=null`) | التطبيع أولًا ثم التحقق: الآن `400` «الدور المختار لا يتبع المشروع المفضل» |
| `communications.occurred_at` إلزامي | فشل تسجيل فتح واتساب (500) | إدخال الحقل صريحًا في `log-contact` |
| تصفير `units.rooms` الفارغ | NULL يربك فلترة الغرف | الهجرة M4 تُثبّت 0 + عرض «غير محدد» |

### 7-3 التحقق اليدوي (curl) المكمّل

- `POST /interests` بأسماء حقول بديلة (`min_price/room_count/is_roof`) → تُكتب في الأعمدة الصحيحة.
- محاولة ربط وحدة بدور من مشروع آخر → `400` «الدور المختار لا يتبع المشروع المفضل»، والصحيح يعيد `floor_id` و«الدور 1» واسم المبنى.
- `GET /units?rooms=4&rooms_op=eq` داخل مشروع ← الوحدة المطلوبة فقط، و`between 3–4` ← وحدتان، و`area 150–200` ← وحدات المؤهلة.
- `GET /interests?rooms_op=gte&rooms=3` ← 7 نتائج، و`between 2–4` ← 14 نتيجة، وفلتر الميزانية ← 20 نتيجة (على بيانات القاعدة القائمة).
- `POST /interests/log-contact` ← `{"ok":true,"count":1,"result":"تم فتح واتساب للمراسلة"}`.
- `GET /units/:id/matches?min_score=0` ← 3 عملاء مهتمين بأعلى نسبة 85% مع الأسباب.
- بناء الواجهة: `cd client && npx vite build` ← **ناجح** (36 حزمة) بعد التعديلات.
